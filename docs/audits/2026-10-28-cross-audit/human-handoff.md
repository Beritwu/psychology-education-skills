## 接续顺序

1. **先确定评分对象。** 可评这些历史产物，也可在修复后重新生成课程，但要明确选择哪一版；不要将本次审计自动套到新课程。
2. **冻结完整材料包。** 使用包含 run_id 的新目录，固定课程文件、产物 revision/hash、规则版本、门禁结果、来源快照与渲染图，并生成独立空白评分表。不要在已填写包上直接执行默认全量 `--export-eval-kit`，本次已复现其课程/评分表可能错配。
3. **提供真正可读的教学材料。** 教师应能读完整脚本/教案、练习及答案，PPT 应提供可编辑文件与渲染图；证据核验者应能定位原始文献快照。导出片段中没出现的章节评价需要补齐，不能推定原项目不存在。材料里的可识别学生资料先脱敏。
4. **教师先独立评，再看 AI 建议。** 按 `benchmarks/rubrics/human_eval.yaml` 填14个核心维度，脚本另评口语自然度；给具体文字理由和 must_fix。建议先不展示 AI 结论，减少先入为主。对无法判断的项目记录缺少什么材料，不编造分数。
5. **记录教师实际修改。** 对同一冻结版本保存修改前后文本、类别与严重度，才能计算真实 Teacher Edit Ratio。AI 建议修改不进入这个指标。
6. **核对并提交。** 先修复/验证本次报告指出的来源分类、API run/mode 转发、评分完整性与版本绑定问题。现有 CLI 路径为 `python -m pebs.cli benchmark --submit-eval <同一冻结包中的worksheet.yaml> --project <匹配的project_id>`；提交前必须确认 worksheet run、project run 与被评 artifact hashes 一致。提交后核对 Store、报告及 skill performance 的绑定状态。现有 Web API 的 run/mode 丢失问题修复前，不依赖它证明绑定成功。
7. **完成至少3个真实课程项目评价。** 本次合成 fixture 历史样例可用于评测准备，但不自动算真实生产项目。三个真实项目的教师反馈回收后，再检查 M6 Acceptance 5 是否满足；其他门禁、证据与正式导出要求独立满足。

## 教师重点复核事项

- A：学生是否理解事实与推测的区别；反例用语是否适合目标班级；渐隐练习能否在计划时间完成。
- B：是否建立学习兴趣而非只强调边界；90分钟活动密度是否合适；真实幻灯片和讲者备注是否足以支持授课。
- C：托育案例与机构实际流程是否一致；待核验主张能否得到可定位的证据；篇幅和授课时长是否合适。
- 三者共同：学科准确性、年龄/情境适宜性、真实课堂反应、教师备课负担。这些不能由两个 AI 的一致意见代替。

## 可复用的 AI 审计流程

冻结并脱敏同一输入 → 两个模型独立报告 → 交换发现逐项质疑 → 本地复现或原文核对 → 保留确认/撤回/未决记录 → 人工复核。

每轮至少保存：源文件哈希、run/版本、模型与调用入口、提示词、原始输出、复现结果、最终裁决。只保存 AI 审计文档；在新增明确隔离的 ai_review 存储接口前，不复用 human_eval API，也不写 performance 注册表。修复实现属于后续单独授权的工作，本次只记录缺陷与验证标准。
